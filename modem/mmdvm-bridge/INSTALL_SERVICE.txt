MMDVM bridge as a service (stream type FRAME)

The bridge talks to the MMDVM or MMDVM_HS board on the real serial port. The modem host
talks to the bridge through a virtual port, so the host knows nothing about the board.

  cd modem/mmdvm-bridge && mkdir -p build && cd build && cmake .. && make
  sudo cp ../mmdvm-bridge.service /etc/systemd/system/        (edit paths first)
  sudo mkdir -p /etc/systemd/system/modem-host.service.d
  sudo cp ../modem-host.service.d/mmdvm.conf /etc/systemd/system/modem-host.service.d/
  sudo systemctl daemon-reload
  sudo systemctl enable --now mmdvm-bridge
  sudo systemctl restart modem-host
  mysql -u root -p modem_host < db/openmt.sql (adds the bridge to the dashboard Services tab)

In the dashboard "port" and "baud" are now the real modem port, and "board" says hotspot
or full. (An older install that has "modem" = mmdvmhs or mmdvm gets the matching "board"
the first time the bridge runs.) The bridge creates any missing setting with its default
at start, and reads them again when the modem host sees a change.

The bridge writes two settings of its own so the modem host can find it: streamType
(FRAME) and bridgePort (mmdvm0, the link /dev/mmdvm0). Use -l to change the link name and
-n for a modem name other than modem1.

Tests: python3 modem/mmdvm-bridge/test/mb_test.py (compares the frames with the ones the
modem host built before the bridge existed).

Clearing a modem that stays keyed in DMR
----------------------------------------
The MMDVM firmware keeps the "DMR started" state the DMR host sets (it keys the transmitter) until it is told off, and only
accepts the off command while the modem is in DMR mode.  A modem that was keyed when its DMR service stopped therefore keys itself
again the next time the mode is DMR.  Whenever the bridge puts the modem in DMR mode it now sends, right after the mode command,
DMR start off and an abort of both slots.  The setting "dmrClear" (config, default true) turns this off.

The MMDVM serial protocol has no reset command.  If the reset pin of the modem is wired to a GPIO line of the computer, the bridge
can reset the firmware when it starts: set "resetGpio" (config) to the line number (default -1: none) and, if it is not the first,
"resetGpioChip" (default /dev/gpiochip0).  The line is pulled low for 100 ms, then high, and the bridge waits for the firmware
to start before it sends its configuration.  Check which line your board uses; a wrong line can reset or drive something else.

A modem that keys itself
------------------------
The bridge asks the modem for its status twice a second and reads the transmitter flag.  If the modem reports its transmitter on
for 5 seconds while the bridge has nothing to send and did not key it (a stuck modem, which the DMR frame timeout cannot see
because the bridge never thought it was transmitting), the bridge puts the modem in its resting mode.  If it is still keyed 5
seconds later and "resetGpio" is set, the modem is reset through that line and configured again.  This applies in simplex and
duplex mode alike.  While the modem reports a signal being received it is not counted (a duplex board repeats it); the 5 seconds
run again from the moment the reception stops, so the hang time must be shorter than that.  Both actions are written to the log.
